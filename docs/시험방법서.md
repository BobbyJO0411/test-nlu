# NLU 기반 반자동 응답 추천 기능 적합도 시험방법서

문서 상태: 사전 검토용 초안. 작성일 2026-10-14, 개정 2026-11-06(한국어 E5 모델, 다중 대표질문·하이브리드 검색, 개발셋 분리, 다수결 규칙, Windows 실행). 실제 시험기관의 성적서 또는 인증서가 아니다.

## 1. 목적과 시험 대상
사용자 시험계획의 ‘NLU 기반 반자동 응답 추천 기능 적합도’를 검증하기 위한 절차이다. 한국어 E5 문장 임베딩(KoE5)으로 사전 등록된 30개 응답 템플릿을 검색하고 고객 질의에 대한 추천 원문을 표시하는 기능을 대상으로 한다. 상표의 등록 가능성 자체를 확정하는 법률판단 도구가 아니다. 사람이 추천을 검토하고 전송하는 반자동 사용 흐름이다.

현재 저장소는 독립된 추천·시험 모듈이다. 기존 제품 백엔드 연결이나 운영 고객 상담 이력에 대한 검증은 포함하지 않는다. 첨부 심사기준 기반의 합성 질의를 사용한다.

## 2. 요구사항 대응
- 실사용 상황을 반영한 질의 100건: data/questions_100.json 및 CSV. 25개 상담 유형별 4건. 실제 고객 원문을 수집한 자료가 아닌 합성 초안이다.
- 템플릿 DB: data/templates.json, 30개 대표 질의·응답과 근거 연결. 전문가 검토 전이다.
- 자동 추천 결과: 실행별 recommendations.json에 추천 원문, 상위 3개 ID·유사도·지연시간 기록.
- 수정 없이 활용 가능 여부: A 실무자, B 변리사 또는 상담 경험자의 독립 이진 판정.
- 정량 설문: 문맥·정확성·완결성·활용성·안전성의 1~5점과 성공/실패 및 이유 기록.
- 불일치: 평가 시작 전에 협의 또는 다수결 중 하나를 정한다. 협의는 이유·참여자·시각을 남기고, 다수결은 A·B와 다른 제3평가자 C가 불일치 건만 블라인드로 판정해 다수 판정을 최종으로 한다.
- 합의율: 협의 이전 A·B의 동일 판정 건수/100. 협의 결과로 최초 판정을 덮어쓰지 않는다.

## 3. 모델과 실행 조건
기본 모델은 nlpai-lab/KoE5(커밋 237b580aea358e3042fcf5baf78124c33c3afd16, MIT, 1024차원, 최대 512토큰)이다. intfloat/multilingual-e5-large를 한국어 triplet 데이터로 미세조정한 공개 모델로, 시험계획의 ‘E5-Ko’ 요건 후보이다. 본 프로젝트에서 추가 학습하지 않았다. 시험기관이 다른 모델을 지정하면 --model-id로 바꾸고 개발셋 튜닝과 100건 실행을 다시 한다. 모델 목록과 고정 커밋은 data/model_profiles.json에 있다. 비교용으로 dragonkue/multilingual-e5-small-ko-v2와 이전 기본값 intfloat/multilingual-e5-small을 개발셋에서 측정했다.

다운로드한 모든 파일은 Hugging Face가 공개한 파일별 SHA256(LFS) 또는 Git blob SHA1과 대조한 뒤 복사본과 verified_model.json을 만든다. 실행 시에는 복사본의 해시를 다시 확인한다. Windows처럼 심볼릭 링크가 없는 환경에서도 같은 검증을 한다. 신뢰할 수 없는 원격 코드는 실행하지 않고, 모델 오류 시 문자 검색으로 자동 대체하지 않는다.

검색: CPU PyTorch, query:/passage: 접두어, 정규화 임베딩의 코사인 유사도, top_k=3. 템플릿 점수는 다음과 같다.
- passage_only: cos(질의, 대표질문+응답 본문)
- multiview_hybrid: α × max cos(질의, 템플릿 대표질문들) + (1−α) × cos(질의, 대표질문+응답 본문) + β × 문자 2~5-gram TF-IDF 최대 유사도
대표질문은 templates.json의 대표질의와 data/template_queries.json의 템플릿별 질문 4개이다. 질문끼리 비교할 때는 E5 안내대로 양쪽에 query: 접두어를 쓴다. α, β는 data/dev_queries.json(개발셋 90건)에서만 격자 탐색으로 정해 data/retrieval_config.json에 기록한다. 시험 질의는 튜닝 단계에서 읽지 않는다. 1위 템플릿의 등록 응답 원문을 그대로 추천한다. 하이브리드 방식이 허용되지 않으면 --beta 0으로 임베딩 단독 실행한다.

옵션 llm_select는 E5 상위 3개 중 OpenAI가 ID를 선택하고 해당 템플릿 원문을 그대로 반환한다. 기존 제품의 자유 생성 모드와 동일하다고 주장하지 않는다. API 인증과 기관 허용 여부 확인 후 별도 실행·평가가 필요하다. 기본 시험은 외부 LLM 없는 template_direct이다.

문자 n-gram TF-IDF 단독(baseline)은 비교용이며 E5/KoBERT 시험 결과에 포함하지 않는다. 추천 점수는 검색 유사도이지 성공 확률이나 평가자 적합도 점수가 아니다.

## 4. 사전 승인 및 동결
1. 담당 실무자와 변리사가 질문, 기준답변, 템플릿, 근거 페이지를 검토한다. 잘못된 최신 기한·수수료, 경과규정, 모호한 문맥을 수정하고 승인한다.
2. 승인자 성명·역할·일시·서명, 데이터셋과 템플릿 SHA256를 별도 승인 기록에 남긴다. data/approval.example.json을 참고해 data/approval.json을 작성한다. 입력된 이름만으로 승인을 인증하지 않는다.
3. 현 데이터셋은 템플릿과 함께 작성되었으므로 독립된 미사용 시험셋이라고 주장하지 않는다. 최종 성적 주장에는 운영 분포를 확인한 추가 독립 질의 100건 또는 기관이 승인한 별도 홀드아웃을 마련한다. 실제 질의의 개인정보는 익명화한다.
4. 평가용 질의는 추천 로직·템플릿·프롬프트 조정에 사용하지 않는다. 현 초안에서 발견된 오류를 개선할 경우 신규 버전·신규 독립 시험셋으로 평가한다. 이미 공개한 100건에서 점수를 올린 결과는 개발 검증으로 표시한다.
5. 합격 기준이 제공되지 않았으므로 임의로 90%, 95% 등의 목표나 합격을 설정하지 않는다. 요구 성능, 시험 모드, 표본 구성과 불일치 절차를 시험기관과 사전에 확정한다.

## 5. 실행 절차
설치: Windows는 `powershell -ExecutionPolicy Bypass -File scripts\install.ps1`, Linux는 `bash scripts/install.sh`. 둘 다 저장소 상위 폴더(NLU_HOME)에 nlu-venv, nlu-model-cache, nlu-models를 만들고 고정 버전 의존성 설치, pip check, 모델 검증, 자동 테스트를 수행한다. 아래 명령의 python은 NLU_HOME/nlu-venv의 Python(Windows: nlu-venv\Scripts\python.exe)이다.

1. 개발셋 튜닝(모델별 1회, 시험 질의 미사용):
python -m nlu.cli tune --model-id nlpai-lab/KoE5 --model-path ../nlu-models/nlpai-lab__KoE5 --report artifacts/evidence/tune_KoE5.json --write-config
2. 승인·동결: scripts/approval_hashes.py로 해시를 출력해 승인서를 작성한다(docs/실질의_수집_및_승인절차.md).
3. 100건 실행:
python -m nlu.cli run --model-id nlpai-lab/KoE5 --model-path ../nlu-models/nlpai-lab__KoE5 --questions data/questions_holdout.json --dataset-type real_anonymized_holdout

생성된 artifacts/runs/<run-id>를 실행 단위로 보관한다. manifest에 Git 커밋과 작업트리 변경 여부(git_worktree_clean), 질의 파일 경로·해시, 모델·검색 설정 해시가 남는다. 정식 실행은 커밋된 깨끗한 작업트리에서 한다. 초기 로딩·인덱싱은 개별 질의 지연시간에 포함되지 않는다. 100건 모두 실행되었는지, case_id 누락·중복이 없는지, 후보와 추천 원문이 템플릿 DB에 있는지 확인한다. 실패한 요청을 임의로 정상 답변으로 채우지 않는다. 환경 실패는 원인을 조치하고 신규 실행ID로 다시 실행하며 기존 실패 로그를 보존한다.

python scripts/build_deliverables.py --run-dir artifacts/runs/<run-id> --out artifacts/review_package

A와 B에게 각각 평가자A_실평가.xlsx, 평가자B_실평가.xlsx를 배포한다. 질의·추천 원문·근거를 제공하되 상대 평가나 모의평가, 기대 템플릿 ID·검색 점수를 먼저 보여주지 않는다. 평가자들은 정량 설문 5개, 성공/실패, 근거, 성명·자격·일시를 직접 입력한다.

불일치 처리와 집계 명령은 docs/평가기준_설문_협의절차.md 4-1절을 따른다(협의: --resolution, 다수결: make_tiebreak_workbook.py와 --c, 두 경우 모두 score에 --decision-rule 지정).

collect_ratings는 파일 실행ID·추천원문 무결성, 100건 완전성, 설문 값, 평가근거와 이름 등을 확인한다. 서명·자격·실제 심사행위의 진위 확인은 시험 담당자의 책임이며 자동 검증이 대체하지 않는다. 원본 서명 자료와 협의 회의록을 별도 보관한다.

## 6. 지표와 산식
전체 추천 응답 수 N=100을 고정한다. 성공 S, 실패 F가 최종 확정되어 S+F=100일 때만 적합도를 확정한다.

적합도(%) = S / 100 × 100
합의율(%) = 최초 A=B인 건수 / 100 × 100

ISO/IEC 25023 FCr-1-G 표기: X = 1 − A/B (A = 최종 실패 수, B = 100). 수학적으로 적합도 ÷ 100과 같으며 집계 파일의 iso_25023 항목에 함께 기록한다.

평가 미완료 또는 협의·다수결 미해결 건이 있으면 최종 적합도는 미산출이다. 스킵·미실행 건을 분모에서 빼고 점수를 높이지 않는다. 협의로 확정된 건수와 최초 일치 건수를 구분해 보고한다. Cohen’s κ와 Wilson 95% 구간은 보조 진단이며 합격 여부를 결정하지 않는다. κ가 정의되지 않는 경우 null로 표시한다. 표본이 합성·편의 표본이므로 신뢰구간을 운영 모집단의 보장으로 해석하지 않는다.

## 7. 표준 표시의 범위
ISO/IEC 25023:2016, ‘8.2.2 Functional correctness measures / FCr-1-G’는 사용자가 제공한 시험 요구문에서 인용한 항목이다. FCr-1-G의 일반적 정의(X = 1 − A/B)를 함께 표기했으나, 본 작업에서는 정식 표준 원문을 열람해 절 번호·지표 코드·측정 단위를 검증하지 않았다(docs/시험기관_확인요청서.md 질문 11). 위 백분율 산식은 사용자 시험계획의 정의를 구현한 것으로, ISO 인증 또는 표준이 정한 합격 기준이라고 표시하지 않는다. 시험기관이 표준 원문 및 개별 응답 성공률 적용 타당성을 확인한 뒤 최종 성적서 표기를 확정한다.

## 8. 결과 확정·보관
모델 커밋·파일 해시, 소스 버전, 의존성 잠금, 질의·템플릿·추천 원문 해시, 실행 환경·로그, 독립 평가 원본, 서명 승인서, 불일치 협의 기록, 최종 집계파일을 함께 보관한다. 모델·템플릿·질의·모드 변경 후에는 신규 실행으로 기록한다. 성적서는 시험기관이 자신의 절차에 따라 발행하며 이 저장소의 문서는 제출 준비 자료이다.
